# LIVE 前台真实点击录制：编码积压修复（2026-09-26）

## 结论与原因边界

用户确认：开打后左键录制，停止后重新 F6 的新进程也失败。已在原版 Steam Godot 4.7.2 / D3D12 Forward+ / RTX 4060 Laptop 的编辑器内嵌游戏中复现相同的双语编码缓存溢出。不是把用户报告归因于旧进程，也不是角色终局判定问题。

不限渲染帧率的前台主循环缺少编码调度余量：最初积压部分消退后，写出仍持续落后于 60fps 输入。对照只改变临时渲染上限，不改编码参数；60fps 上限消除了本机此条件下的持续积压。此结果支持主循环与编码的资源争用判断，**未进一步把瓶颈唯一归因于 CPU、GPU 或某个驱动线程**。

历史直接发 `button_up` 的通过结果不覆盖真实前台点击条件，本次不以那些结果替代新验证。

## 最小生产改动

仅 `scripts/ui/battle_recorder.gd` 的 LIVE 渲染预算生命周期：

- LIVE 启动时保存 `Engine.max_fps`。原来为 0（不限）或大于 60 时临时设为 60；已有低于 60 的上限保持。
- 正常完成、启动失败、场景退出释放预算；若其他拥有者在期间主动改值，不覆盖其新值。重复申请/释放不破坏原值；英文副本不持有全局预算。
- 不改 `Engine.time_scale`、物理频率、战斗属性、结束/续录判定、VSync 或磁盘设置。
- 输出继续为 1080×1920 / 60fps / 中英文双份；NVENC p4 / constqp 16、软件编码配置、像素/颜色转换和原有 `filter_threads=2` 均不变。
- 不扩大 120 帧 / 256MiB 写入器上限，不添加丢帧规避。SIM 没有新增限速申请路径。

**用户可见差别：录制期间游戏显示渲染最多 60fps，录制结束恢复原上限；不是把成片降为低帧率。**

## 独立 MP4 核验

`validation/verify_foreground_movies.py` 对四份成片调用 FFprobe `-count_frames` 完整解码计数，合计 **25752 帧**，stderr 无解码错误；不是只读取容器标称帧率。

- 四份均 H.264 / yuv420p / 1080×1920 / 60/1，各 **6438 帧、107.300000 秒**。
- AAC / 48kHz / 双声道；音轨时长均 107.300000 秒。同局中英文的压缩音轨 SHA-256 一致，前七秒实际音频 RMS 非零。
- 两个时刻抽帧并查看八格接触表：普通对局保留中英 VS，盔甲架为中英介绍且无 VS；角色、弹体、伤害数字和位置发生变化，没有工具栏/鼠标覆盖，不是空白或静止成片。
- BT.709 色彩空间标记存在；transfer/primaries 未单独标记，未将其写成“全部颜色标记齐全”。编码质量参数未改；码率随内容变化，不用码率相等作为判据。
