# LIVE 首帧准备误计时 / 几秒中断修复（2026-09-26）

## 分类与实际原因

录制系统：不修改角色、伤害、AI、威胁或地图。此次是左键 LIVE 编码队列保护触发，与已修复的盔甲架旧胜利铃问题不同。

- 用户真实日志：普通烈焰人 vs 骷髅仅36帧；盔甲架89/106/129帧。错误均为“编码速度跟不上：录制缓存已满”。保存配置确为 `tail_seconds=100.0`。
- 用户环境：Steam Godot `4.7.2.stable.steam.ed1daf0bf`、D3D12 Forward+、RTX4060 Laptop。此前短测使用配套引擎/OpenGL，未覆盖这一渲染路径。
- 同一 Steam 引擎、山巅、双语言原始编码基线：OpenGL录1153帧正常；D3D12在122帧中断，复现同一调用栈。
- D3D12首次画面准备/读回约1.7–2秒，旧逻辑将其计入录像时钟：首次观察已有104待写帧、实际只写出2帧，随后触发有界队列上限。不是100秒续录设置失效，也不能据此断言持续编码速度必然不足。
- 隔离候选仅把GPU准备移至正式时钟前：同一D3D12路径1031帧/17.18秒正常，未改编码质量或扩大缓存。

## 修复范围

- `battle_recorder.gd`：LIVE先绘制并验证中英文首帧；准备完成后才起音画时钟与速度监测基准，准备阶段音频也不进入成片。不在正式录制中重置时钟或吞掉已经捕获的帧。
- 准备阶段可取消；读回或音频失败仍明确退出。工具栏显示“准备中…”，不是已正式开录。
- `battle_record_controls.gd`：异常中断即使保留下部分MP4，也明确显示“录制中断…不是完整对局”，不只显示已保存。
- 保留256MiB/120帧队列上限、异步积压/减速/音频保护；不降分辨率、帧率、质量，不关闭保护，不更改游戏速度。
